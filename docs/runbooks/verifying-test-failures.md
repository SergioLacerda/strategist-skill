# Runbook: Triaging a Failing `tests/spec/` Test

## Trigger

`go test -tags spec ./tests/spec/...` fails, and it's unclear whether it's a
genuine regression from your current change, a pre-existing unrelated
issue, or a flaw in the test itself.

## Steps

1. Reproduce the failure directly — re-run the specific failing test with
   `-run <TestName> -v`, don't rely on a pasted log alone.
2. Check provenance before assuming it's your fault: `git status --porcelain
   -- <affected path>` and `git log --oneline -3 -- <affected path>`. If the
   affected file/state is unchanged by your session and was already
   committed before you started, it's pre-existing — say so explicitly,
   don't silently "fix" something unrelated to your task without flagging it.
3. Read the failing test's own source, including inline comments — the
   comment often states the test's *intended* narrow purpose, which may be
   broader or narrower than what the code literally checks. A mismatch
   between stated intent and literal implementation is itself a common bug
   class (see Decision Point, category C below).
4. Classify the failure:
   - **(A) Genuine regression** — your change broke something the test
     correctly guards. Fix your change, not the test.
   - **(B) Pre-existing, unrelated to your task** — confirmed via step 2.
     Don't silently fix it as a side effect of unrelated work; surface it
     and let the user decide whether to address it now or separately.
   - **(C) The test itself is flawed** — e.g. checks a broader condition
     than its stated intent (a bare `os.Stat` where only a directory should
     matter, not any file), or depends on non-hermetic environment state
     (files generated by tools external to this repo, live repo-root state
     unrelated to what's actually being verified).
5. For category (C), apply this repo's hermeticity principle: tests should
   validate `strategist-skill`'s own structure and authored content, not
   couple to external tools' generated output or incidental filesystem
   noise. When narrowing a check's precision (e.g. adding an `IsDir()`
   guard) is enough to fix it without losing its actual intent, prefer
   that over removal. When the check is fundamentally about validating a
   *different* project's output, remove it from this repo's suite — that
   project should test its own contract in its own suite.
6. Before removing any test or helper, `grep` for other call sites first —
   shared helpers may have multiple callers; removing one caller's test
   doesn't mean the helper is dead.
7. Verify: `go build ./...`, `go vet ./...`, the specific test with `-run`,
   the full `go test -tags spec ./tests/spec/...`, and `go test ./...` for
   the non-spec packages — a fix isn't done until all four are clean.

## Decision Point

**All four verification commands pass, and the fix matches one of the
three categories above with an explicit rationale recorded:** the fix is
complete. Note in the commit/report which category applied and why.

**Any verification command still fails, or you can't confidently place the
failure in category A/B/C:** stop, don't guess. A test failure you can't
explain is not safe to silently work around.

## Stop Conditions

- Category (B) pre-existing issues found while working on something else —
  don't fix opportunistically without flagging; scope creep hides intent.
- Removing a shared helper/test without checking all call sites first —
  confirmed empty `grep` result required before deletion.
- Any of the four verification commands fails after the fix — not done.
