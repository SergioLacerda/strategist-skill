## Release gate checklist

### Local verification

- [ ] Select a clean release commit containing only the intended `v1.0.17`
  scope.
- [ ] `make release-check` passes.
- [ ] `make release-verify` passes, including CI, documentation, fixture,
  vulnerability, reproducibility, and embedded-skill gates.
- [ ] `make release-test` produces the six platform/architecture snapshot
  artifacts.
- [ ] `make check-release-artifacts` passes for the snapshot.
- [ ] `make release-reproducible-check` passes.
- [ ] The documentation generation gate reports no drift.
- [ ] The landing application CI gates pass.
- [ ] The final snapshot is generated from the clean selected commit and has
  version `1.0.17`.

The current checkout must not be used as the final release snapshot. It
contains unrelated in-progress changes and is reported as dirty by Git.

### Published artifact verification

GoReleaser is configured to produce six platform/architecture binaries,
`SHA256SUMS`, and release assets named `strategist-<os>-<arch>`. After
publication, verify separately:

- [ ] The tag is exactly `v1.0.17` and points to the verified release commit.
- [ ] No GitHub Release already exists for `v1.0.17` before workflow start.
- [ ] Every expected binary and `SHA256SUMS` asset is present and non-empty.
- [ ] Cosign bundles exist for every published binary/checksum asset.
- [ ] SBOM and GitHub build-provenance attestation are present.
- [ ] `make check-release-assets TAG=v1.0.17` passes against the published
  release.
- [ ] Download, checksum, signature, and installation verification succeeds on
  the supported platform matrix.

Local snapshot files prove build output only. They do not prove GitHub asset
publication, signature availability, SBOM upload, or attestation completion.

## Tooling and environment notes

- Release verification depends on the Go version declared by `go.mod`, network
  access for dependency/tool downloads, and enough writable temporary disk for
  Go build and GoReleaser caches.
- A local vulnerability-tool update is present in the dirty worktree but is
  not part of the committed `v1.0.16..HEAD` release range until explicitly
  committed and reviewed.
- If a gate fails because of cache or disk quota, preserve the failure output,
  clean only the relevant cache with explicit approval, and rerun from the
  same clean candidate.

## Rollback and stop conditions

Stop before tagging or publishing when any of these occurs:

- the selected release commit is dirty, ambiguous, or differs from the
  reviewed inventory;
- `v1.0.17` already has a tag or GitHub Release;
- release verification, generated documentation, embedded catalog, or lock
  checks report drift;
- GoReleaser artifacts are missing, duplicated, or have unexpected names;
- checksum, Cosign, SBOM, attestation, or published-asset verification fails.

Rollback target: keep `v1.0.16` as the last-known-good published boundary. Do
not move or delete it. Preserve failed snapshot/release evidence for diagnosis
and rerun only from a corrected, independently verified commit.

## Publication handoff

This document prepares the release but does not create a tag, push Git history,
call GitHub Release APIs, or upload assets. Those actions require a separate
explicitly authorized release operation after all unchecked gates above pass.
